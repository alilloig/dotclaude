lfg reviewer GitHub App

Setup guide · 2026-10-16 · one bot identity that reviews and approves your PRs

Summary

The lfg skill now posts reviews as a GitHub App bot. The bot approves the PR when a fresh re-checker confirms that each finding is fixed or validly refuted. Phase 6 merges only with a current bot approval.

You must do steps 1–4 by hand once. GitHub requires a browser for App creation. Until you do them, lfg works as before: reviews post as you, and there is no approval gate.

How the flow works

1. Create the App

  1. Open github.com/settings/apps/new.
  2. GitHub App name: a unique name, for example alilloig-lfg-reviewer. The bot login becomes <slug>[bot].
  3. Homepage URL: any URL, for example your GitHub profile.
  4. Webhook: clear the Active box. lfg calls the API. It does not receive events.
  5. Repository permissions:
    PermissionAccessWhy
    Pull requestsRead and writePost reviews, approve, request changes
    ContentsRead-onlyRead the diff for review anchors
    MetadataRead-onlyMandatory; GitHub sets it
    Do not give any other permission. The bot must not push code.
  6. Where can this GitHub App be installed? Select Only on this account.
  7. Click Create GitHub App. Write down the App ID from the General page.
  8. On the same page, click Generate a private key. The browser downloads a .pem file.

2. Install the App

  1. In the App settings, open Install App and select your account.
  2. Select All repositories. New repos then get the bot automatically.

Repos without the App. On a repo where the App is not installed (for example, an organization repo), lfg records reviewer_login = none. It then posts as you and skips the approval and the merge gate.

3. Store the credentials

Replace <APP_ID> and the download filename, then run:

mkdir -p ~/.config/lfg && chmod 700 ~/.config/lfg
mv ~/Downloads/<app-name>.*.private-key.pem ~/.config/lfg/reviewer-app.pem
chmod 600 ~/.config/lfg/reviewer-app.pem
cat > ~/.config/lfg/reviewer-app.env <<EOF
LFG_REVIEWER_APP_ID=<APP_ID>
LFG_REVIEWER_APP_KEY=$HOME/.config/lfg/reviewer-app.pem
EOF
chmod 600 ~/.config/lfg/reviewer-app.env

Keep the key out of git. The key lives outside ~/.claude, so the dotclaude repo never sees it. If the key leaks, delete it in the App settings and generate a new one.

4. Verify

S=~/.claude/skills/lfg/scripts
bash $S/app_token.sh --configured && echo configured
bash $S/app_token.sh --login                          # expect <slug>[bot]
bash $S/app_token.sh <owner> <repo> | wc -c          # expect ~40+; never print the token

If --login fails with HTTP 401, put the App's Client ID in LFG_REVIEWER_APP_ID and try again.

Then do one end-to-end run on a throwaway PR in an owned repo. Check these results:

  1. The Phase 3 review shows the bot as the author, not you.
  2. Phase 4 ends with a bot Approved review, or with Changes requested and a list of open items.
  3. Phase 6 merges only after the approval.

Branch protection (optional). If you set "Require approvals: 1", test that the bot approval satisfies it. GitHub does not document this for Apps. Community reports say it counts. Do not enable "Require review from Code Owners", because an App cannot be a code owner.

What changed in the skill

FileChange
scripts/app_token.shNew. Signs an RS256 JWT with openssl, finds the repo installation, and mints a token. The token is limited to one repo with pull_requests:write and contents:read.
scripts/post_review.shPosts as the bot when it gets a token. If not, it falls back to you for COMMENT only. It accepts APPROVE and REQUEST_CHANGES events.
scripts/run_state.sh + testNew keys reviewer_login and review_round, with validation. All tests pass.
SKILL.md Phase 0New "Reviewer App" section: it resolves the bot login for each repo.
SKILL.md Phase 3The first review is always COMMENT. The Codex orchestrator still must not approve.
SKILL.md Phase 4New findings.json ledger. New step 7: a fresh re-checker, the jq gate, a maximum of 2 rounds, then APPROVE or REQUEST_CHANGES.
SKILL.md Phase 6Merge gate: the bot's latest review must be APPROVED on the current head commit.

The changes are not committed. They are in the working tree of the dotclaude repo.
